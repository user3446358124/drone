# 蓝方通用优化：代码审计、方案与实测

日期：2026-10-05。项目：Swarm-Rescue-v4。

## 1. 本轮目标与结论

从“图一简单但分低”和“图五健康度低”两个现象入手，提高完成率、完成速度和健康度。新增规则只依赖无人机允许读取的传感器、通信、已观测地图及任务进度，不根据地图编号或炸弹固定坐标切换策略。

当前保留的是 `approach_v9` 候选，源代码身份为：`f18b6f023902534af5a98da92f0a53121d51e1a68aa58da27dae3988934b4638`。这是全部 `src/**/*.py` 文件相对路径和内容哈希的汇总，不是单个文件的哈希。

## 2. 为什么图一分数低，图五损失在哪里

代码中的比赛分数为：

`总分 = 0.6 × 归位百分比 + 0.2 × 健康百分比 + 0.2 × 时间分`

`时间分 = 100 × clip((步数上限 − 已用步数) / (0.5 × 步数上限), 0, 1)`

探索分权重为零，但有效搜索仍决定能不能找到最后的炸弹。时间分在使用一半步数之前封顶，之后线性下降。

- 图一上限2000步，想拿满20分时间奖励，需要1000步内完成。用户原表1951步只剩4.9%的时间分，实际贡献0.98分。即使10枚全部归位、健康90.2%，仍只有 `60 + 18.04 + 0.98 = 79.02`。问题主要是完成得太晚，地图视觉上简单不能替代对时间预算的判断。
- 图五上限7200步，满时间分门槛为3600步。用户原表5462步、健康25.8%，对应 `60 + 5.16 + 9.66 ≈ 74.82`，健康和耗时同时损失。
- 提供的10月4日PDF使用了更新版本和多种布局，图五历史布局已经3051步、健康54.2%、90.84分。因此原表不是当前版本的完整基线。本轮重新运行项目原始代码作对照，不能把跨版本、跨平台的不同成绩直接说成优化收益。
- 在超过半程的区间，图一每节省100步约增加2分，图五每节省100步约增加0.56分；提高10个百分点健康度，两者都增加2分。相同的避障绕路在图一代价更大。

评分函数自身不以“已经全部归位”为时间分前提。如果真实时间超时导致未完成的比赛提前结束，仍可能显示部分时间分。本轮同时检查完整归位、实际归位数和耗时，没有把这种提前结束当作完成速度提升，也没有改变评分规则。

还可以把绕路是否划算算得更具体：10架、每架初始健康50时，某一架少扣1点血只增加总分0.04。在半程之后，时间每多一步损失`40/步数上限`分。所以图一为避免一架扣1点血，多花2步就已抵消健康收益；图五约为7.2步。毁机和丢失炸弹的风险另算，不能只按这条小损伤换算。半程之前时间分虽封顶，但仍要留出余量，避免最后一项任务越过半程门槛。

对应实现：`src/swarm_rescue/simulation/reporting/score_manager.py`。

## 3. 整体流程与各部分需要的信息

每步先更新处置奖励、队友状态、目标观测、处置区和在线地图，再根据自身载荷与任务状态选择动作。执行动作后，若策略要求停住，则利用测得速度主动制动。

| 体系部分 | 需要考虑的内容和信息 | 本轮选择的方法 | 为什么这样选择 |
|---|---|---|---|
| 搜索与覆盖 | 语义探测范围、LiDAR可通行范围、已搜索格、队友搜索目标、剩余任务 | 保留原巡航与共享前沿框架，修正语义覆盖距离 | LiDAR看到空地不等于语义传感器已经检查过炸弹，错误覆盖会漏搜索 |
| 障碍建图 | LiDAR距离与方向、GPS/指南针、语义类别、队友墙体和清除消息 | 有限证据栅格；确认是动态对象时清除该射线端点的旧墙假设 | 移动炸弹和无人机不能永久变成墙；只清端点，避免大片抹除邻近墙体 |
| 目标记录 | 观测距离、角度噪声、已有目标中心、队友发现、近距离相邻目标 | 远距离允许较宽的关联半径，近距离保持较窄；队友中心平滑更新 | 远观测的世界坐标误差更大；统一窄半径会把同一炸弹拆成多个任务，统一宽半径又会合并相邻炸弹 |
| 任务分配 | 当前任务、租约、新鲜队友位置、健康、载荷、任务实际进展 | 保留分布式竞价与租约；增加相邻接近区域预约、编号裁决和载荷优先 | 减少多人同时抓同一片区域造成的纠缠；失效或停滞预约可以让位；此候选仍存在按编号切换负责人过于频繁的问题 |
| 远距离接近 | 目标可见不代表直线路径通畅；已观测障碍、当前规划、LiDAR | 距离大于65像素时走在线规划，到近处再正面对齐 | 先绕开墙角和阻挡，再处理抓取姿态，避免全程只转向加直冲 |
| 近距离抓取 | 目标距离与角度、邻近其他炸弹、启动阶段、队友载荷 | 对齐且距离不超过35时才开抓手；更近的其他炸弹会抑制启动 | 引擎抓手是碰撞接触装置，且不强制单炸弹单持有者；过早常开可能抓错或形成多机共同拖拽；本候选没有保留逐目标等待4步的试验 |
| 搬运返航 | 在线地图、载荷造成的空间要求、处置区观测、往返轨迹、逃逸状态 | 载荷膨胀32像素、空载20；载荷在线路径采用已有侧向移动；规划失败时保留轨迹与局部绕行兜底 | 搬运时机身加炸弹需要更大空间；返航不能只靠转头再前推，也不能无限等待完整地图 |
| 局部避障与恢复 | 前方距离、语义载荷掩码、阻塞计数、已排队逃逸动作 | 修复逃逸动作执行条件，保留原局部避障与任务停滞恢复 | 原逻辑触发逃逸后重置计数，却还要求计数达到另一个高阈值才执行，导致已排队动作被漏掉 |
| 搬运进度与交接 | 任务进展、回程轨迹、恢复尝试、可用健康队友 | 本候选暂保留原恢复机制：检查停滞、重规划，必要时交接 | 此机制存在旧轨迹进度度量和重试计数被清零的问题；修复试验造成其他场景退步，仍需独立验证后再纳入 |
| 等待、对齐、退役 | 平移指令是否为零、测得速度、朝向、传感器是否缺失 | 在零平移指令时加反向制动力；有传感器缺失时沿用原命令 | 动作是力而不是速度，零输入不能立刻停住；避免等待或原地转向时继续漂移碰撞 |
| 计算预算 | 地图像素数、目标定位抖动、搜索次数、物理运行速度 | 用距离变换膨胀障碍，限制噪声目标导致的逐步重规划 | 省下规划开销可以让控制更及时；实时扣血和墙钟超时也使计算效率影响最终成绩 |

这里的65、35、32、20等阈值是根据现有运动与传感器尺度采用的工程参数，尚未通过跨任务规模系统寻优。它们没有按地图编号设置，也不构成最优性证明。

## 4. 从代码中确认的关键事实

1. **零平移输入不是停车命令。** 模拟器给机体施加力，速度依靠阻尼逐渐衰减。原地对齐、等待任务等阶段也可能撞墙。本轮只给“要求停住”的动作增加制动，没有用速度控制替换全部动作。
2. **碰撞扣血按真实时间冷却。** `DroneAbstract.collide_wall/collide_drone` 共用计时器，超过真实一秒后才扣一次。因此固定随机种子也不能保证不同机器、不同负载下完全一致；健康变化还可能改变竞价和后续轨迹。本轮保持计时器、物理、比赛评分不变。
3. **语义传感器约200，LiDAR约300。** 搜索覆盖应按语义可见范围计算；导航建图仍可以利用更远的LiDAR。本轮把覆盖采样上界收至182，给传感器离散和误差留余量。
4. **抓手可多机附着同一炸弹。** 控制策略必须用观测和队友任务提前协调。没有读取炸弹真实持有者列表来规避这个问题。

逐目标抓取前4步稳定期也做过试验，尚未保留。它只是提供消息传播和裁决的机会，不是引擎里的原子互斥锁，不能保证唯一附着。
5. **在线规划只处理已观测障碍。** 膨胀、禁止对角切墙、路径平滑和局部LiDAR有助于避障，但不能保证未观测空间安全。现有双向加权A*限制最多5000次展开，其目标是有限计算预算内得到可用路径，不保证真实地图全局最短。
6. **处置区和目标位置来自带噪观测。** 目标变化超过24像素时仍需允许重规划，但设置至少12步的更新间隔，避免每帧抖动都触发A*。载荷定期65步、空载90步重规划。
7. **发现目标、抓到目标和完成目标是不同时间。** 一个失败回放中，最后目标第387步已发现，但认领在多架无人机之间变动，第1842步才附着。仅看末尾回放会误判为“漏搜”。本轮试验过较早任务优先和距离优势迟滞，但没有获得足够稳定的全局收益，所以暂未纳入保留候选。后续代价应考虑实际绕墙路线，不能把欧氏距离差当作完整处置成本。
8. **反复卡住不应不断回到首次恢复。** 原恢复代码把任意新进度用来清零载荷恢复次数，短暂逃逸也可能抹掉失败历史。本轮试验过按实际执行路线计算进度、保留同次附着恢复历史；图三完成率恢复，却又出现其他布局退步。这是需要继续解决的方向，不能在本报告中写成保留候选已经解决的能力。

## 6. 为什么没有保留一些看起来更高级的方案

- 全动作速度闭环曾把健康度提高到接近100%，但多个试验只能完成5至6枚。载荷惯性、传感器速度噪声、抓取接近和原状态机不能直接套用统一速度环。这一版已撤回。
- 全阶段侧向导航也出现完成率下降。最终只在载荷在线路径阶段使用现有侧向移动函数，保留近距离对齐和抓取方式。
- 单纯加大障碍膨胀会保护健康，但也可能封死本来可走的窄口，造成时间和任务损失。最终采用空载/载荷区别，不继续无限加宽。
- “已经验证的轨迹永远优先”和“连续健康竞价”有理论理由，但联合试验出现图四从完整归位降到9/10，另有返航耗时退步。这组变化没有保留。未来需要逐项消融，不能将这次联合失败解释为其中每一项都无效。
- 提前让所有空闲无人机进入前沿搜索也做过试验，但图一分层布局仍9/10，图五相邻布局降至76.10分。这次试验没有保留。进一步查日志确认早期线索已经存在，接近阶段负责人反复切换才是应优先修复的问题；不能把每一种拖尾都当成漏搜索。
- 只按最早认领保持负责人，虽然修复了图一分层布局和图五相邻布局，却使图二、图三历史布局出现9/10。随后加入明显距离优势才换人的迟滞规则，图二恢复完整归位，图三仍未完成，因此这组也没有直接保留。
- 修复实际路径进度和保留恢复失败历史，使图三重新完整归位，但图一相邻布局出现8/10。再加入近距离连续观察4步后启动抓手的试验，图三又出现8/10。这些结果说明组件的理论合理性不能替代组合的完整评测。
- 最终候选是多项修改的组合。已有对照能证明组合的实测变化，不能准确把每一分收益归因给某一个修改。

## 7. 泛用性边界与后续优先级

本轮新增方法依靠观测、物理约束和任务状态，可以跨布局和地图使用；源代码未读取离线布局或地图真值。离线坐标只用于评测器设置场景。

当前证据仍不足以说已经达到用户要求的稳定泛用性。本轮交付的是实验候选、问题定位与可复现对照，而不是已经验证可普遍替代原版的正式升级。

Map07尤其说明这一点：原版5276步、健康46.2%、87.26分，候选7928步、健康59.6%、78.89分。多保住13.4个百分点健康度，增加2.68分；多用2652步，损失约11.05分，结果反而少8.37分。健康改善需要与完整处置工期一起定价，不能作为独立的优化目标。

但原控制器中仍有按地图尺寸和无人机编号选择的巡航路线、开局角色，这部分原有逻辑没有全面重写。**新增优化具有地图独立性，并不意味着整个继承的控制器已经完全地图无关。** 本轮也没有验证无人机数量变化、炸弹数量变化、特殊区域开启、通信故障或对抗红方任意新布局。

继续优化的顺序建议：

先固定多布局、多种子的回归集，将调参图和最终验证图分开；组件修改应逐项消融，至少同时检查完整归位、平均分、明显退步和最慢任务。Map07这次结果不再用于重调代码，保留为独立检验。

1. 优先处理剩余炸弹和最后返航。记录每枚目标首次发现、认领、附着、归位时间，将拖尾区分为漏搜、接近失败、返航失败和错误任务记录。先提高完整归位概率，再在图一的1000步门槛附近优化。
2. 用可观测自由空间图分配搜索区域，逐步替换原尺寸分组巡航。分别维护“几何空闲”和“语义已搜索”，按尚未检查区域的价值/到达成本选择前沿；不能把超出语义距离的空地提前排除。
3. 把目标关联升级为不确定度模型。远观测坐标分布、近距离复核和相邻炸弹多假设，比只调一个距离半径更可靠；当前宽关联仍可能误合并很近的不同炸弹。
4. 搬运规划采用速度与载荷姿态相关的空间余量，并检查窄口可通行性。当前32像素只是静态近似，不能完整表示炸弹摆动和转弯扫掠。
5. 将相邻接近预约约束收紧到真正发生物理争用的阶段。当前规则可能让本来可并行的近邻目标顺序执行，安全收益与吞吐损失还需要逐项评测。
6. 竞价从“到目标的欧氏距离”升级为“接近加返航的路线成本、碰撞风险和剩余预算”。比赛时间看的是最后一枚归位时刻，分配目标应优先降低最大的预计完成时间，而不只是总路程：让远、绕路、拥堵的任务早点有负责人。原规则没有直接最小化完整处置工期，试验的70像素迟滞也只是防抖折中。
7. 若继续引入学习模块，优先评估搜索价值预测或局部动作选择，保留可解释的任务状态和抓取约束；先建立多布局、多种子训练/验证拆分，再决定是否值得替代规则。

还有一个任务规模边界：原控制器的等待和完成判断依然使用`_EXPECTED_BOMBS = 10`。当前`MiscData`只提供地图尺寸、无人机数量、时间限制和任务模式，没有公开炸弹总数。因此这版不能直接宣称支持任意炸弹数量；若比赛允许数量变化，需要先设计不依赖固定总数的搜索停止条件或使用规则允许的任务总数接口，不能读取地图真实炸弹列表来补齐信息。

这些是下一步候选，没有在本轮把未验证的算法描述成已经实现或必然涨分。

### 下一版更合适的组合方式

- **信息层先保证“知道什么”的准确性。** 分开保存几何空闲、语义已搜索、待复核目标和已附着载荷；目标用位置不确定度与复核记录，避免把远距离线索直接当成精确实体编号。
- **分配层按预计完整归位时间安排任务。** 利用允许的通信共享到达与返航估计，保留切换成本和租约；仅在收益足以覆盖重新接近、重新确认和交接损失时换人。通信不完整时退回本地可解释规则，不能用全局Python变量绕过通信限制。
- **路线层按得分的时间门槛选风险。** 预计能在半程前完成时，可以花适量路径代价保健康；接近门槛或已经超出时，绕路必须有足够健康收益或防毁机收益。载荷需要方向与转弯空间估计，静态统一加宽不能代替这个判断。
- **执行层保留明确的抓取与恢复约束。** 短暂停车、对齐、唯一接近区域、可用队友确认等可继续用基础算法。进度跟随实际动作路径，恢复要有升级机制，并考虑剩余时间是否够交接完成。
- **学习模块先做预测。** 如果后续使用网络，优先预测路段通行时间、碰撞风险或搜索价值，让基础规划与分配使用这些预测；先验证它是否改善预计归位时间，再考虑直接输出动作。当前实验尚未证明网络是解决这些问题的必要条件。
